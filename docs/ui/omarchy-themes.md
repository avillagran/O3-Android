# Importing Omarchy themes into Android

Companion to [UI_SPEC.md](../UI_SPEC.md) section 3.1. ot3 reads the live Omarchy
theme from disk; a phone has no Omarchy install, so the themes are converted once, on a
machine that has Omarchy, into a JSON asset that ships in the APK.

## Source

- Omarchy 4.0.2 (MIT), `omarchy:themes/<name>/colors.toml`, 22 themes: catppuccin,
  catppuccin-latte, ethereal, everforest, flexoki-light, gruvbox, hackerman, kanagawa,
  last-horizon, lumon, lupine, matte-black, miasma, nord, osaka-jade, retro-82,
  ristretto, rose-pine, solitude, tokyo-night, vantablack, white.
- `colors.toml` is the canonical file. No theme ships `alacritty.toml` or `shell.toml`;
  those are generated into the current-theme directory from templates
  (`omarchy:default/themed/alacritty.toml.tpl:30,40`,
  `omarchy:default/themed/shell.toml.tpl:127-131`), and the shell template sets the
  popup background, text and border ot3 uses to `background`, `foreground` and the
  active border.
- ot3 parses `colors.toml` with `^\s*([a-zA-Z0-9_]+)\s*=\s*["'](#[0-9a-fA-F]{6})["']`
  (`ot3:ui/qml/T3Palette.qml:26`): quoted six-digit hex only, either case. The
  generator uses the same rule and fails on any other value form for a required key.

## Keys

| Key | Required | Used for | ot3 fallback |
|---|---|---|---|
| `background`, `foreground`, `accent` | yes | base palette | `color0`, `color7`, `color4` (`omarchy:shell/Commons/Color.qml:161-164`) |
| `muted` | no | Commons muted | `color8`, else foreground |
| `red` | yes | `failed` | `color1` (`omarchy:shell/Commons/Color.qml:159`) |
| `green`, `yellow`, `blue`, `magenta` | no | `done`, `waiting`, `working`, `input` | accent (`ot3:ui/qml/T3Palette.qml:10-16`) |
| `orange` | no (missing in white, solitude, last-horizon) | `warning` | yellow, then accent (`ot3:ui/qml/T3Palette.qml:15`) |
| `cyan`, `bright_blue`, `bright_magenta` | no | project slot palette | accent, then removed as a duplicate if the accent is already in the palette (`ot3:ui/qml/T3Palette.qml:17-22`) |
| `mode` | no | cross-check only | — |
| `selection`, `*_background`, `*_foreground` variants | — | not read by ot3 | — |

`black` and `bright_black`, which `ot3:ui/js/DocumentTheme.js:3-9` reads for web
documents, exist in no installed theme, so the generator ignores them.

## Light or dark

ot3 decides with three slightly different rules: Rec.601 luma below 0.5 for documents
(`ot3:ui/js/DocumentTheme.js:4`), Rec.709 luminance above 0.5 for the sky
(`ot3:ui/qml/T3Starfield.qml:58`), and HSL lightness below 0.5 for MCP apps
(`ot3:ui/qml/T3Backend.qml:1076`). For all 22 themes the three rules and the theme's own
`mode` agree (17 dark, 5 light: catppuccin-latte, flexoki-light, lupine, rose-pine,
white; checked 2026-10-25). Android uses **one rule, the sky's Rec.709 luminance of
`background` > 0.5 → light**, and the generator fails if it disagrees with `mode`, so a
future theme that splits the rules is caught at import time instead of on a phone.

## Output

`app/src/main/assets/themes/omarchy-themes.json`, committed, regenerated by hand when
Omarchy adds or changes themes or the lib changes `theme.tokens`. Schema 2: each theme is
the lib's `theme.tokens` result for its `colors.toml`, as it is (keys sorted, layout below
stable), so ot3 and Android cannot drift:

```json
{
  "schema": 2,
  "source": { "omarchyVersion": "4.0.2", "lib": "lib-t3-rust 0.3.4 (e2ec546)", "generatedAt": "2026-10-26T00:34:57Z" },
  "themes": [
    {
      "id": "tokyo-night", "name": "Tokyo Night", "appearance": "dark", "luminance": 0.1071, "mode": "dark",
      "base": { "background": "#1a1b26", "foreground": "#a9b1d6", "accent": "#7aa2f7", "muted": "#414868", "red": "#f7768e", "…": "…" },
      "roles": { "dim": "#6b718a", "statusMuted": "#6f758f", "divider": "#272936", "surface": "#21222e", "…": "…", "onAccent": "#1a1b26" },
      "layers": { "dim": { "color": "foreground", "alpha": 0.57 }, "…": "…" },
      "statusColors": { "working": "#7aa2f7", "approval": "#eb927b", "": "#6f758f", "…": "…" },
      "projectPalette": ["#7aa2f7", "#9ece6a", "…"],
      "projectFills": ["#272e44", "…"],
      "sky": { "lightSky": false, "star": "#a9b1d6", "meteor": "#ffffff", "ink": 1.0,
               "header": { "brightness": 1.25, "nebula": 0.55, "meteorRate": 0.85, "base": "#…" },
               "panel": { "brightness": 0.5, "nebula": 0.0, "meteorRate": 0.3 } },
      "document": { "appearance": "dark", "variables": { "--background": "#1a1b26", "…": "…" } },
      "mcpTheme": "dark"
    }
  ]
}
```

- `roles` are what ot3 draws: Qt Quick's 8-bit premultiplied blend of the foreground or
  accent at the alphas in `layers` (listed in [tokens.md](tokens.md) section 1) over the
  background. Before UI-1f this file computed them with straight alpha, one step off on
  one channel for about a third of the roles.
- `base` has `null` for a colour the theme lacks (`white` has no `orange`); the app reads
  only the ones present. `projectPalette` keeps ot3's slot order with duplicates removed;
  a missing key gives the accent, as ot3's `pick()` does.
- The Material containers `accentContainer` and `failedContainer` (tokens.md section 2)
  are not ot3 roles and not in this file: `Ot3Colors` blends them at load time until the
  lib returns them (LIB_REQUESTS.md, "theme.tokens: Material containers").
- The same function serves themes read at run time: `ThemeTokens.fromColorsToml(text, id)`
  (`core/theme/ThemeTokens.kt`) calls `theme.tokens` through `DomainEngine`; Material You
  builds a `colors.toml` from the wallpaper scheme and goes through it too.

## Generator

`tools/import-omarchy-themes [THEMES_DIR] [--omarchy-version V] [--check]` runs
`./gradlew :core:importOmarchyThemes`: a JVM test task (`OmarchyThemesImport`, skipped in
ordinary test runs) that loads the host `libt3_jni.so` (`scripts/fetch-or-build-lib.sh
--host-jni`), passes every `THEMES_DIR/*/colors.toml` (default
`/usr/share/omarchy/themes`) to `theme.tokens` and writes the result. It computes no
colour. It fails on a theme without `background`, `foreground` or `accent`, or whose own
`mode` disagrees with the lib's `appearance`. Rerunning on the same themes and lib keeps
`generatedAt`, so the output is byte-identical; `--check` writes nothing and fails on any
difference. `ThemeTokensAppTest` checks that the committed tokyo-night and
catppuccin-latte entries equal `theme.tokens` over the two `colors.toml` files kept in
`core/src/test/resources/omarchy/`, and `OmarchyThemeCatalogTest` checks them against the
goldens in [tokens.md](tokens.md).

Later (not v1): import a user's own `colors.toml` through the Storage Access Framework,
through the same `ThemeTokens.fromColorsToml`.
